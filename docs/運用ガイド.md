# 運用ガイド

デバッグ演習を進めるときの手順と、指導担当が押さえておきたいポイントをまとめます。

## 出題の組み方

段階ごとの組み合わせの例です。一度に渡すチケットは2〜3枚程度にし、1枚ずつ取り組ませるのがおすすめです。

| 段階 | 組み合わせの例 | 狙い |
|---|---|---|
| 基礎形成期(最初の演習) | B01、B02 | フロントとバックエンドのどちらの問題かを切り分ける |
| 基礎形成期(慣れてきたら) | B03、B06 | ログやSQLを観測して、遅さの原因を測って探す |
| 補助生成期 | B05、B07 | 外部の記録や自分で作った基準と突き合わせて検証する |
| 委任期 | B04、B08 | トランザクションと並行処理のメンタルモデルを確かめる |

同じバグを仕込んでも、スタックを変えれば別の演習として使えます。たとえば Node.js 版で B03 を経験した若手に、Rails 版の B03(ORM の遅延読み込み)を出すと、同じ問題が別の形で現れることを体験できます。

## 当日の進め方

1. 演習用リポジトリを渡し、README に沿って起動してもらう(初回は数分かかるので、事前に起動しておいてもらうとスムーズです)。
2. AI の利用範囲を伝える。基礎形成期は「AIなし」か「概念の質問のみ」、補助生成期以降は「利用可。ただし提案をどう検証したかを調査ログに残す」が目安です。
3. チケットを1枚選んでもらい、時間を区切って取り組ませる(目安:★☆☆ 30分、★★☆ 60分、★★★ 90分)。
4. 時間内に解けなくても、調査ログをもとに振り返りを行う。

## 振り返りの観点

答えにたどり着いたかどうかより、調査の過程を中心に振り返ります。

- 推測と事実を区別できていたか。報告者の推測(「お客様の環境の問題かも」など)をそのまま信じていなかったか。
- 最初の切り分け(フロントかバックエンドか、アプリかDBか)を早い段階で行えたか。
- 再現手順を自分で作れたか。特に B08 のように、再現に工夫がいるバグで確認します。
- 修正後に、直ったことをどう確かめたか。
- AI を使った場合、AI の提案をそのまま採用せず、事実で裏付けてから採用したか。

各バグの `answer.md` の「指導のポイント」に、バグごとの問いかけの例があります。

## 運用上の注意

- 出題記録(どのチケットがどのバグか)は、若手に見えない場所で管理してください。
- 演習用リポジトリを若手どうしで共有すると答えが伝わってしまうので、同じ組み合わせを使い回す場合は、時期をずらすか、スタックやバグの組み合わせを変えてください。
- 若手が委任期に近づいたら、新しいバグを考えて仕込む側に回ってもらうのも効果的です。README の「新しいバグを追加する」の手順で追加できます。
