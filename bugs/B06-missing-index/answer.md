# 注文番号のインデックスがない

| 項目 | 内容 |
|---|---|
| レイヤー | DB |
| 難易度 | ★★☆ |
| 推奨段階 | 基礎形成期の後半〜補助生成期 |
| 主に鍛える力 | 観測、仮説と切り分け |

## 原因

`orders.order_number` にインデックスがないため、注文番号での検索のたびに、300万件の注文テーブルを全件走査しています。データが少なかったサービス開始直後は問題にならず、注文が増えるにつれて遅くなりました。

| スタック | 該当箇所 |
|---|---|
| 共通 | `db/init.sql` から `idx_orders_order_number` の作成を削除 |

## 想定される調査の流れ

1. 検索APIの応答時間をログで確認し、遅いのがサーバー側の処理であることを確かめる。
2. 「データが増えるにつれて遅くなった」「DBのCPUが高い」という報告から、DBのクエリを疑う。
3. 検索で実行されているSQLを特定し、psql で `EXPLAIN ANALYZE` を実行する。`Seq Scan`(全件走査)になっていることを確認する。
4. テーブルのインデックスを `\d orders` で確認する。

## 正しい修正

`CREATE INDEX idx_orders_order_number ON orders (order_number);` を追加します。演習環境では、psql で直接実行して効果を確かめたうえで、`db/init.sql` にも反映させます。

発展として、注文番号は一意であるべきなので、一意制約(UNIQUE)にするのがより適切ではないか、という議論もできます。

## 再発防止の例

- 新しい検索条件を追加するときに、実行計画を確認することをレビュー観点にする。
- 本番相当のデータ量で性能を確認する環境を用意する。
- 遅いクエリをログに出す設定(`log_min_duration_statement`)を入れる。

## 指導のポイント

- 「遅い」という報告に対して、どこで時間がかかっているかを測ってから原因を探せたかを見ます。
- `EXPLAIN ANALYZE` の読み方を、このタイミングで一緒に確認すると効果的です。インデックスがあるときとないときで実行計画がどう変わるかを、自分の目で見比べさせてください。
- 演習環境では差が数百ms程度ですが、本番ではデータ量や同時アクセス数によって、これが数秒やDB全体の負荷につながることを補足してください。
