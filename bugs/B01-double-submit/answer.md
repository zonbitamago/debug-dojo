# 二重送信による二重注文

| 項目 | 内容 |
|---|---|
| レイヤー | フロントエンド |
| 難易度 | ★☆☆ |
| 推奨段階 | 基礎形成期 |
| 主に鍛える力 | 観測、再現 |

## 原因

注文ボタンが、処理中も押せる状態のままになっています。利用者がボタンをダブルクリックしたり、反応が遅いと感じて連打したりすると、注文APIが複数回呼ばれ、そのたびに注文と決済が行われます。

| スタック | 該当箇所 | 仕込んだ変更 |
|---|---|---|
| React | `frontend/src/components/OrderForm.tsx` | `disabled={submitting}` と、処理中の早期 return を削除 |
| Vue | `frontend/src/components/OrderForm.vue` | `:disabled="submitting"` と、処理中の早期 return を削除 |

ボタンの表示は「処理中…」に変わるため、見た目では対策されているように見える点がポイントです。

## 想定される調査の流れ

1. 問い合わせの注文をDBで確認し、同一ユーザー・同一商品で数百ms差の2件があることを確かめる(事実の確認)。
2. バックエンドのログで、同じタイミングに `POST /api/orders` が2回届いていることを確認する。サーバー側で二重に処理しているのではなく、リクエストが2回来ていると切り分ける。
3. ブラウザの開発者ツールのネットワークタブを開いた状態でボタンをダブルクリックし、リクエストが2回飛ぶことを再現する。
4. 注文フォームのコンポーネントを読み、処理中に再度押せてしまうことを特定する。

## 正しい修正

処理中はボタンを無効化し、ハンドラの先頭でも処理中なら何もしないようにします(正解版のコードを参照)。

あわせて議論したいのは、フロントエンドだけで防ぐのは十分か、という点です。通信の再送や、ブラウザ以外からのAPI呼び出しでは同じ問題が起きます。本来は、冪等キー(リクエストごとの一意なID)をサーバー側で受け取り、同じキーの注文を重複して作らないようにするのが堅牢な対策です。演習では、ここまで気づけるかを問いかけてみてください。

## 再発防止の例

- 送信を伴うボタンのレビュー観点に「処理中に再度押せないか」を加える。
- 注文APIに冪等キーを導入する。

## 指導のポイント

- 「サーバーが2回処理したのか、リクエストが2回来たのか」を最初に切り分けられたかを確認します。ここを飛ばしてコードを読み始めると、バックエンドを疑って時間を使いがちです。
- 「毎回は起きない」という報告から、利用者の操作(連打)を仮説に挙げられたかも見るポイントです。
- AIに「二重注文が起きる」とだけ聞くと、トランザクションやDBの一意制約など、もっともらしい別の原因を挙げることがあります。症状の事実(リクエストが2回届いている)を先に確定させてからAIに相談させると、AIの提案を検証しやすくなります。
