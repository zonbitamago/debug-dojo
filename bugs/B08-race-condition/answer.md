# 在庫の更新で競合状態が起きている

| 項目 | 内容 |
|---|---|
| レイヤー | 並行処理 |
| 難易度 | ★★★ |
| 推奨段階 | 委任期(補助生成期の後半でも可) |
| 主に鍛える力 | 再現、仮説と切り分け、検証 |

## 原因

在庫を確保する処理が「在庫を読み取る → アプリ側で在庫が足りるか判定する → 計算した在庫数で上書きする」という手順になっています。複数の注文が同時に処理されると、同じ在庫数を読み取った処理同士が互いの更新を上書きし(いわゆる lost update)、在庫を超えて注文が成立します。

正解版では `UPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ?` のように、判定と更新を1つのSQLで行っているため、この問題は起きません。

| スタック | 該当箇所 |
|---|---|
| Node.js | `backend/src/inventory.ts` の `reserveStock` |
| Rails | `backend/app/services/inventory.rb` の `reserve`(`find_by` して `update!`) |
| Java | `backend/src/main/java/.../InventoryService.java` の `reserve` |

## 想定される調査の流れ

1. 注文データで、腕時計の注文件数と在庫数を確認し、「10個しかないのに売れた件数」と「在庫の減り方」が合わないことを事実として押さえる。
2. 1件ずつ注文する分には正しく動くことを確認し、同時に注文したときだけ起きるという仮説を立てる。
3. 在庫を10に戻し、15件程度の注文を同時に送るスクリプトを書いて再現する。例として、シェルなら `curl` を `&` で並列に実行する方法があります。
4. 在庫を確保するコードを読み、読み取りと更新の間に他の処理が割り込める箇所を特定する。

## 正しい修正

判定と更新を1つのSQLで行う形に戻します。`SELECT ... FOR UPDATE` で行ロックを取ってから更新する方法もあり、両者の違いを説明させると理解が深まります。

修正後は、同じスクリプトで同時に注文を送り、成立件数がちょうど10件、在庫が0になることを確認させてください。

## 再発防止の例

- 在庫や残高など、同時に更新されうる値の更新は、アプリで計算した値の上書きではなく、DB上での加算・減算と条件付き更新で行うことをコーディング規約にする。
- 並行実行のテスト(同時に複数リクエストを送るテスト)を用意する。

## 指導のポイント

- 自分で並行リクエストのスクリプトを書いて再現できたかを、特に重視してください。再現できないバグは、直ったことも確かめられません。
- AIが生成するコードでは、ORM の「取得して、変更して、保存する」パターンがよく使われ、この問題がそのまま紛れ込みます。AIのコードをレビューするときの観点として定着させてください。
- 正解版では、決済の応答を待つ間ずっと在庫の行ロックを握っているため、同時注文は1件ずつ順番に処理されます。正しく動く一方で性能面の課題があることも、発展的な議論の材料になります(B04 の解説も参照)。
