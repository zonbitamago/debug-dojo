# 在庫の確保がトランザクションの外で行われている

| 項目 | 内容 |
|---|---|
| レイヤー | バックエンド |
| 難易度 | ★★★ |
| 推奨段階 | 補助生成期〜委任期 |
| 主に鍛える力 | 仮説と切り分け、再現 |

## 原因

注文処理は「在庫の確保 → 注文の作成 → 決済 → 確定」を一つのトランザクションで行い、決済に失敗したらすべてをロールバックする設計です。ところが在庫の確保だけがトランザクションの外で実行されているため、決済に失敗してロールバックしても、減らした在庫が元に戻りません。

| スタック | 該当箇所 | 仕込んだ変更 |
|---|---|---|
| Node.js | `backend/src/orderService.ts` | `reserveStock(client, ...)` を `reserveStock(pool, ...)` に変更。トランザクション中の接続ではなく、プールの別の接続で実行される |
| Rails | `backend/app/services/order_service.rb` | 在庫の確保を `transaction do` ブロックの外に移動 |
| Java | `backend/src/main/java/.../OrderService.java` | `@Transactional` を付けたメソッドを、同じクラスの別メソッドから呼び出す形に変更。自己呼び出しではプロキシを経由しないため、トランザクションが効かない |
| Go | `backend/order_service.go` | 在庫の確保を `s.pool.Begin` の前に移動し、トランザクションではなくプール(`s.pool`)で実行 |

Node.js 版は1単語の違い、Java 版は Spring の有名な落とし穴で、どちらもコードを読むだけでは気づきにくいバグです。Go 版は Rails 版と同じく、在庫の確保を先に済ませてからトランザクションを始める形です。Java 版ではトランザクション全体が無効になるため、決済に失敗した注文が `pending` のまま残るという追加の症状も出ます。

## 想定される調査の流れ

1. ロボット掃除機を2台注文して与信上限エラーを起こし、その前後で在庫数を比較して再現する(5万円を超える決済は必ず与信上限エラーになる。決済代行の仕様書を参照)。
2. 「注文は作られていないのに在庫だけ減る」という事実から、処理の途中で失敗したときに一部の変更だけが残っている、という仮説を立てる。
3. 注文処理のコードを読み、トランザクションの範囲と、各SQLがどの接続(どのトランザクション)で実行されているかを追う。
4. 必要に応じて `LOG_SQL=1` やDBのログで、`BEGIN` と `UPDATE products` の順序や接続を確認する。

## 正しい修正

在庫の確保を、注文の作成・決済と同じトランザクションの中で実行するように戻します。

発展として、外部の決済APIをトランザクションの中で呼んでいること自体の是非も議論できます。決済の応答を待つ間、在庫の行ロックを握り続けるため、人気商品では注文が詰まる原因になります。「在庫を仮押さえして、決済後に確定する」などの設計も含めて考えさせると、委任期向けの課題になります。

## 再発防止の例

- 決済に失敗したときに在庫が元に戻ることを確認する結合テストを書く。
- Java であれば、`@Transactional` の自己呼び出しをレビュー観点や静的解析で検出する。

## 指導のポイント

- トランザクションの範囲を、図やコメントで説明できるかを確認します。「どのSQLがどの接続で実行されるか」というメンタルモデルがあるかどうかで、調査の速さが大きく変わります。
- AIに注文処理のコードを渡して「問題はあるか」と聞くと、見つけられることも見逃すこともあります。見逃した場合は、AIの説明を鵜呑みにせず、実際に失敗させて確かめることの大切さを伝える良い題材になります。
