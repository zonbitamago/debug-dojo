# 決済APIのタイムアウト設定が効いていない

| 項目 | 内容 |
|---|---|
| レイヤー | 設定・外部連携 |
| 難易度 | ★★★ |
| 推奨段階 | 補助生成期 |
| 主に鍛える力 | 観測、仮説と切り分け、検証 |

## 原因

`docker-compose.yml` で、決済APIのタイムアウトを設定する環境変数の名前が誤っています。正しくは `PAYMENT_TIMEOUT_MS` ですが、`PAYMENT_TIMEOUT` になっているため設定が読まれず、コード側の既定値(1秒)が使われています。

決済代行の仕様では、1万円を超える決済は追加認証のため1.5秒程度かかります。そのため1万円を超える注文だけがタイムアウトになり、自社側では注文をロールバックしてエラーを返します。一方、決済代行側では処理が続いて承認されるため、「エラーなのに請求される」状態になります。

| スタック | 該当箇所 |
|---|---|
| 共通 | `docker-compose.yml` の `backend` の環境変数 `PAYMENT_TIMEOUT_MS` を `PAYMENT_TIMEOUT` に変更 |

コードには一切手を入れていないため、コードだけを読んでいても原因にたどり着けない点がこのバグの特徴です。

## 想定される調査の流れ

1. 1万円以下と1万円超の商品を注文し、金額によってエラーになることを再現する。
2. バックエンドのログで、決済APIの呼び出しがタイムアウトしていることを確認する。
3. 決済代行の処理記録(http://localhost:4010/charges)で、同じ注文番号の決済が承認されていることを確認する。自社と決済代行で結果が食い違っていることを事実として押さえる。
4. 決済代行の仕様書で応答時間を確認し、タイムアウトの設定値を疑う。
5. タイムアウトの値がどこから来ているかをコードから追い、環境変数の名前が一致していないことを見つける。

## 正しい修正

環境変数の名前を `PAYMENT_TIMEOUT_MS` に戻します。

ただし、これは直接の原因を取り除いただけです。タイムアウトしたときに「決済されたかどうか分からない」状態をどう扱うかという、より本質的な問題が残ります。決済代行への照会や取消、冪等キーを使った再試行など、委任期向けの発展課題として議論できます。

## 再発防止の例

- 必須の設定値が未設定のときは、既定値で動かさずに起動時にエラーにする。
- 起動時に、読み込んだ主要な設定値をログに出す。
- 決済代行との突き合わせ(自社の注文と決済の記録が一致しているか)を定期的に行う。

## 指導のポイント

- 「自社のログ」と「外部サービスの記録」の両方を見て、食い違いを事実として確認できたかを見ます。
- 仕様書(`payment-mock/README.md`)を読みにいけたかも重要です。外部連携の不具合では、相手の仕様の確認が調査の近道になることがよくあります。
- コードを読んでも見つからないとき、設定や環境の違いに目を向けられたか。AIにコードだけを渡しても原因は見つからないので、「AIに渡す情報が足りているか」を考えるきっかけにもなります。
