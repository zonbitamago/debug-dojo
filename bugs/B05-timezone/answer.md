# 日別集計のタイムゾーンの誤り

| 項目 | 内容 |
|---|---|
| レイヤー | バックエンド(SQL) |
| 難易度 | ★★☆ |
| 推奨段階 | 補助生成期 |
| 主に鍛える力 | 観測、検証 |

## 原因

日別に集計するときの日付を、日本時間ではなくDBセッションのタイムゾーン(UTC)で求めています。日本時間の0時〜9時の注文が前日に計上されるため、どの日も数字がずれ、当日分は特に少なく見えます。

| スタック | 該当箇所 |
|---|---|
| Node.js | `backend/src/report.ts` |
| Rails | `backend/app/controllers/reports_controller.rb` |
| Java | `backend/src/main/java/.../ReportRepository.java` |
| Go | `backend/report.go` |

いずれも `(created_at AT TIME ZONE 'Asia/Tokyo')::date` を `created_at::date` に変更しています。

## 想定される調査の流れ

1. psql で、日本時間の日付で集計するSQLを自分で書き、画面の数字と比較する。ずれていることを事実として確定させる。
2. ずれ方(当日が少ない、各日が少しずつずれる)から、日付の境界がずれているという仮説を立てる。
3. 境界付近(日本時間の0時〜9時)の注文がどちらの日に計上されているかを確認して、仮説を検証する。
4. `SHOW timezone;` でDBセッションのタイムゾーンを確認し、レポートのSQLを特定する。

## 正しい修正

集計の日付を日本時間で求めるように戻します。

## 再発防止の例

- 日付の境界をまたぐテストデータ(日本時間の0時30分など)で、集計結果を確認するテストを書く。
- 「日時は保存も比較もUTC、表示と集計の単位だけ業務のタイムゾーン」という方針をチームで明文化する。

## 指導のポイント

- 「経理の数字が正しい」と決めつけず、自分で集計して突き合わせられたかを見ます。正解の基準を自分で作る力は、検証の基本です。
- `timestamptz` がどう保存され、どう日付に変換されるかを説明させてください。タイムゾーンは、AIの生成コードでも誤りが起きやすく、テストもすり抜けやすい領域です。
