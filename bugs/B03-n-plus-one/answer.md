# 注文履歴の N+1 クエリ

| 項目 | 内容 |
|---|---|
| レイヤー | バックエンド |
| 難易度 | ★★☆ |
| 推奨段階 | 基礎形成期の後半〜補助生成期 |
| 主に鍛える力 | 観測、仮説と切り分け |

## 原因

注文履歴を取得する処理で、注文の一覧を取得したあと、注文1件ごとに商品名を取得するクエリを発行しています。佐藤さんは注文が1,200件あるため、1回の画面表示で1,201回のクエリが実行されます。田中さんは5件なので遅さに気づきません。

| スタック | 該当箇所 | 仕込んだ変更 |
|---|---|---|
| Node.js | `backend/src/orderRepository.ts` の `findOrdersByUser` | JOIN をやめ、ループの中で商品名を取得 |
| Rails | `backend/app/controllers/orders_controller.rb` の `index` | `.includes(:product)` を削除 |
| Java | `backend/src/main/java/.../OrderRepository.java` の `findByUser` | JOIN をやめ、RowMapper の中で商品名を取得 |

Rails 版は1行を消しただけの、最も典型的な N+1 です。

ただし Rails 版では、リクエスト中の同じ SQL の結果を再利用するクエリキャッシュが働くため、DB に実際に届くクエリは8回(注文の取得1回と商品7種類)です。ログには `Completed 200 OK in 124ms (... (1201 queries, 1193 cached) ...)` のように出ます。遅さは正解版の2〜4倍程度と、他のスタックより差が小さくなります。DB 側のログや統計だけを見ていると N+1 に気づきにくいので、「キャッシュされていても、Ruby のオブジェクトを1,200回組み立てるコストは残る」ことも含めて振り返ると効果的です。

## 想定される調査の流れ

1. 佐藤さんと田中さんで注文履歴APIの応答時間を比べ、件数に比例して遅くなっていることを確かめる。
2. 「佐藤さんの環境の問題かもしれない」という報告を鵜呑みにせず、サーバー側の応答時間をログで確認する。
3. `LOG_SQL=1` にしてSQLのログを出し、同じ形のクエリが大量に実行されていることを見つける(Rails 版はリクエストのログにクエリ件数も出ます)。
4. 該当するコードを特定する。

## 正しい修正

JOIN(Rails では `includes`)で、商品名を1回のクエリでまとめて取得します。

発展として、そもそも1,200件を一度に返す設計でよいのか(ページングが必要ではないか)も議論の材料になります。

## 再発防止の例

- 開発環境でリクエストごとのクエリ件数を監視し、閾値を超えたら警告を出す(Rails なら Bullet、`strict_loading` など)。
- 件数の多いテストデータで性能を確認する。

## 指導のポイント

- 報告者の推測(「お客様の環境の問題かも」)と、確認した事実を区別できたかを見ます。
- 「件数が多いと遅い」という観測から、N+1 という仮説にたどり着けたか。仮説がなくても、SQLのログを見るという観測の手段を思いつけたかが重要です。
- AIが生成したコードでは、ORM の関連の遅延読み込みが原因の N+1 がよく紛れ込みます。AIの出力をレビューするときの観点として定着させてください。
